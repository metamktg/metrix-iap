0. Scope statement — read before building anything

This build produces a fully mocked, fully typed frontend prototype. No live backend calls, no live Supabase project, no live LLM analysis calls, no live Meta API. Every diagnosis, score, and decision in this prototype is generated from static/seeded mock data, not computed at runtime. Structure the code so a real backend and a real analysis engine can be dropped in later without touching component code. lib/supabase.ts is a typed stub client only, clearly commented // TODO: real Supabase project not connected this pass.

Do not try to provision Supabase tables. Do not try to call any external AI API to generate the "diagnosis" text. Write it as realistic static content instead.

1. What Metrix IAP actually is

Metrix IAP is not a generic analytics dashboard concept, it's a specific internal methodology already in production use at Meta Marketing Agency, running on a fixed pipeline:

Raw Meta Ads exports
→ DATA BUNDLE PREP        (normalize + validate two paired CSV exports into one bundle)
→ ANALYSIS CORE           (11-dimension read: buyer-intent funnel, traffic quality,
                            audience psychology, creative DNA, messaging themes,
                            cross-dimensional patterns, variable extraction,
                            performance tiers, failure patterns, confidence scoring,
                            winning variable stack)
→ REPORT SUMMARY          (client-ready document)
→ STRATEGY MAP            (ICP registry, message pillars, scaling playbook)
→ BRIEF BUILDER           (production-ready creative briefs)
→ [optional] MST path     (Matrix Sprint Test: creative-scan validation →
                            post-launch test-engine read of rows/columns/diagonals)
→ OPTIMIZATION LOOP       (re-weights variables, sets budget allocation, feeds
                            back into Strategy Map and Brief Builder)

Build the UI around this exact pipeline, not a generic "ingest/label/diagnose" restatement of it. Every screen in this prototype is a window into one stage of that pipeline.

Real taxonomy to use throughout (do not invent substitutes)

Confidence labels (every insight, every decision card carries exactly one):


high — >100 conversions OR >$1,000 spend with a consistent pattern
medium — directional, below the high threshold
validation_required — promising signal, insufficient spend or time
insufficient — cannot support action


Performance tiers (every creative/ad is classified into exactly one):


Tier 1 — Scale Winners (high ROAS + strong buying intent + efficient acquisition)
Tier 2 — Optimize Candidates (high intent with a bottleneck, or solid performance with iteration potential)
Tier 3 — Test / Pivot (mixed signals, needs controlled retest)
Tier 4 — Eliminate (poor performance across multiple metrics, clear failure pattern)


Optimization/budget allocation bands (Decision Feed and Sprint Matrix should reference these, not invented percentages):


Critical Scale — 60% budget band, +20% lift vs baseline
Scale — 25% band, +10–19% lift
Optimize — 10% band, 0–9% performance
Validate — 5% band, new/unproven
Retire — −20% or worse


Decision Feed action verbs (product-facing, keep these, they're the human-readable layer on top of the tiers above): Scale, Hold, Isolate, Kill, Rebuild, Retest, Brief Next Sprint. Every decision card must tag its underlying tier + confidence label alongside the action verb, so the UI-friendly verb is always traceable to the real classification system underneath it. Don't let these float free of each other.

Variable code families (reference in Creative Signal tab, don't invent new ones): CN_ concept, FW_ framework/angle, HK_ hook, TN_ tone, CTA_ call-to-action. Show these as short badges next to creative names (e.g. HK_ProofFirst, FW_ProblemSolution), not as prose.

ICP profile schema (Strategy-adjacent fields, use in Account Intelligence and Workspace Home wherever an ICP appears): profile_id, profile_name, demographic_foundation, psychographic_profile, behavioral_signals, funnel_entry_point, performance_data, message_resonance, strategic_recommendation, confidence_level.

MST matrix logic (Sprint Matrix tab): a matrix test has rows (cross-avatar variable signals), columns (avatar/ICP-specific patterns), and diagonals (maximum variable isolation). Every tested variable resolves to one of: universal_winner, avatar_specific, underperformer, neutral, insufficient_data.

Dark premium interface. Deep navy/near-black background, white/off-white type, electric blue accents, amber/gold for priority states, red reserved for true risk/critical only.
