You are acting as a senior product engineer, UX architect and design-systems lead working on Metrix IAP.

Your task is to comprehensively revise the existing application based on the requirements below. This is an implementation task, not an audit or proposal. Inspect the current codebase, create a concrete implementation plan, execute the changes, validate the complete experience and fix regressions before finishing.

PRODUCT INTENT

Metrix is not meant to feel like another reporting dashboard.

It is the decision layer for paid advertising. It converts fragmented marketing data into:

1. Signals
2. Analysis
3. Decisions
4. Strategy
5. Hypotheses
6. Creative briefs
7. Tests
8. Reports

The core product principle is:

“Decision first. Data second.”

Every primary screen must answer, in this order:

1. What changed?
2. Why does it matter?
3. What should the user do?
4. How confident is Metrix?
5. What evidence supports the recommendation?
6. What remains unknown?

Do not begin by redesigning individual cards in isolation. Fix the global application structure, hierarchy and shared components first, then revise each module.

NON-NEGOTIABLE EXECUTION RULES

- Inspect the complete route structure, shared layouts, database schema, generated types, API contracts, state models and design tokens before changing anything.
- Create and follow a route-by-route implementation checklist.
- Implement the revisions. Do not stop after producing recommendations.
- Preserve all working data connections, authentication, authorization, account switching, URL parameters and existing functional workflows.
- Do not delete working capabilities to make the interface appear cleaner.
- Do not replace working functionality with placeholders, mock data or static UI.
- Do not silently suppress backend errors. Fix their root causes and provide safe user-facing recovery states.
- Do not expose database tables, schema fields, stack traces, internal object names or raw server errors to users.
- Use reusable components and centralized design tokens. Do not solve the same design problem separately on each route.
- Preserve old URLs through redirects or route aliases if navigation destinations are moved.
- Use additive and reversible database migrations where schema changes are required.
- Run typecheck, linting, automated tests and route-level regression checks before completion.
- Do not consider the task complete while visible state contradictions, layout regressions or failing tests remain.
- Do not ask broad design questions that can be resolved from these requirements. Only stop for a genuine blocker that would materially change product behaviour.

PHASE 5: DESIGN SYSTEM AND PREMIUM VISUAL LANGUAGE

Keep the premium dark Metrix identity, but reduce visual noise.

1. Colour

Create semantic colour tokens.

Use:

- Metrix blue/cyan for primary interaction
- Green for confirmed success or positive outcome
- Amber for caution or incomplete evidence
- Red for blocking error or destructive action
- Purple only if it has one permanent semantic meaning
- Neutral colours for structure and secondary metadata

Do not use colour alone to communicate state.

Reduce:

- Excessive glow
- Multiple bright borders
- Gradient usage on secondary navigation
- Simultaneous coloured tags
- Coloured category and status systems that conflict

2. Surfaces

- Reduce unnecessary cards inside cards.
- Use whitespace and typography before adding another border.
- Maintain consistent border radius.
- Use one standard border treatment.
- Use elevation sparingly.
- Avoid large empty containers.
- Avoid wrapping one short data point in multiple nested surfaces.

3. Typography

Implement a centralized type scale.

Recommended desktop scale:

- Page title: 24 to 28px
- Section heading: 17 to 20px
- Card title: 15 to 16px
- Body: 14 to 15px
- Metadata: 12 to 13px with accessible contrast
- Button text: 13 to 14px

Requirements:

- Use sentence case for user-facing content.
- Reserve all-caps for short eyebrow labels and statuses.
- Reserve monospace for IDs and technical detail.
- Use tabular numerals for performance data.
- Use approximately 1.4 to 1.5 line height for body copy.
- Do not allow primary explanations to truncate without an accessible expansion.
- Limit visible tags to three, then show “+N more.”

4. Spacing

Use a consistent 8px spacing system.

Suggested values:

- Page padding: 24px minimum on desktop
- Section spacing: 24 to 32px
- Card padding: 16 to 20px
- Grid gap: 16px
- Dense row height: minimum 40 to 44px
- Primary interactive control height: approximately 40px or greater

5. Buttons and interactions

Standardize:

- Primary button
- Secondary button
- Tertiary/text action
- Destructive action
- Icon button
- Selected toggle
- Disabled state
- Loading state

Each surface should have one obvious primary action.

Do not style multiple adjacent actions as equally primary.

- Opening the workflow panel must not obscure content.

- Drawers and modals must fit within the viewport.
- Primary actions must remain accessible at reduced heights.
- Sticky elements must not overlap one another.

Meet WCAG 2.2 AA expectations where applicable:

- Normal text contrast of at least 4.5:1.
- Essential UI and graphical component contrast of at least 3:1.
- Pointer targets at least 24x24 CSS pixels or correctly spaced.
- Visible keyboard focus.
- Logical tab order.
- Escape closes dialogs and drawers.
- Focus is trapped inside open modals.
- Focus returns to the triggering control after close.
- Controls have accessible names.
- State is not communicated by colour alone.
- Screen-reader labels exist for icon-only controls.
- Reduced-motion preference is respected.
