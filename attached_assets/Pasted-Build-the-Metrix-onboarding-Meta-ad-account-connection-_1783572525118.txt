Primary product goal:

1. Enter email on the Metrix waitlist/signup form.
2. Be approved or simulated-approved for the pilot.
3. Log in after approval.
4. Click “Connect Meta Ad Account.”
5. Complete Meta OAuth using ads_read only.
6. Return to Metrix through the OAuth callback route.
7. Metrix calls /me/adaccounts with the returned user token.
8. User sees available ad accounts returned by Meta.
9. For this pilot only, confirm that act_1202182091204847 is available.
10. User selects the test ad account.
11. Metrix saves the selected account to Supabase.
12. Metrix runs the two IAP report pulls against the selected account.
13. Normalized rows land in report_rows.
14. Dashboard reads from report_rows, not mock data or seeded data.

OAuth flow:
- User clicks Connect Meta Ad Account.
- Start Meta OAuth with scope ads_read only.
- On callback, exchange the short-lived user access token for a long-lived user access token.
- Store access_token_encrypted and token_expires_at.
- Before every report pull, check token_expires_at.
- If expired or near expiry, prompt the user to reconnect.
- Do not silently fail.
- Do not expose the token to the browser after callback.
- Do not log access tokens.
- Do not store access tokens in raw API response logs.

Token security:
- Store Meta app secret server-side only.
- Store Meta client secret / app secret in environment variables only.
- Do not expose secrets to the frontend bundle.
- Encrypt stored user access tokens before writing to Supabase.
- Use a server-side TOKEN_ENCRYPTION_KEY environment variable or Supabase Vault if available.
- Never persist Graph API paging.next URLs containing access_token.
- Before storing any raw Meta response, sanitize:
  - remove access_token query params from paging.next
  - remove token values from URLs
  - store paging cursors and redacted next URLs only
- If raw_response/raw_pages are stored, they must be token-sanitized first.

Flattening rule:
- Convert each nested item into deterministic metric keys.
- Example:
  actions[{action_type:"landing_page_view", value:"1"}] -> metrics.actions.landing_page_view = 1
  cost_per_action_type[{action_type:"landing_page_view", value:"0.32"}] -> metrics.cost_per_action_type.landing_page_view = 0.32
  action_values[{action_type:"offsite_conversion.fb_pixel_purchase", value:"100"}] -> metrics.action_values.offsite_conversion_fb_pixel_purchase = 100
- Replace dots in action_type keys with underscores.
- Preserve the original action_type string in raw_response/raw_pages.
- Do not fabricate metrics that Meta does not return.
- Missing metrics should be null or absent, not invented.
- Derived metrics may be calculated only when formula logic is explicit and traceable.

125 consolidated metric target:
The template expects the full 125-metric schema. Implement coverage as:
1. Direct mappings where the API returns the metric directly.
2. Nested mappings from actions/action_values/cost_per_action_type/ROAS arrays where available.
3. Nullable placeholders for template metrics not returned by the selected date/account/objective.
4. A metric_mapping_status field or debug object showing mapped, missing, derived, and unavailable metrics.

Do not claim 100% metric parity in the UI unless all required template metrics are either mapped, derived with an explicit formula, or intentionally null because Meta did not return that metric for the account/date range/objective.
