Checked the current sidebar markup directly. Every child link inside these groups calls the **same page function** regardless of label — clicking any of them lands on an identical page with no distinct content:

- **Analysis** group → "Executive Lens / Creative Lens / Audience Lens / Risk Lens" all call `showPg('analysis')`, just toggling a display filter, not real subpages.

- **Audience Intel** group → "ICP Registry / Age×Gender Heatmap / Platform Split / Placement & Device" — all four call `showPg('audience')`. Same page, four labels.
- **Strategy** group → "Map / Audience / Creative / Communication / KPI Forecast" all call `showPg('strategy')`. Only "Brief Queue" and "Recommendations" actually route elsewhere.

**Fix required:** each labeled nav child needs its own real route/page state, or at minimum its own anchor/tab within the parent page that actually scrolls to or renders distinct content. Relabeling without rewiring is the current failure mode — don't repeat it in the rebuild below.

## 3. Cross-cutting UX requirements (apply to every new subpage above, not just one)

**A. Stat tiles per subpage, scoped to that layer.**
Every subpage needs top-of-page KPI tiles relevant to *its own analytical layer* — not the same global spend/CPA tiles repeated everywhere. Example: Hypothesis Queue's tiles should be things like "active hypotheses," "validated this cycle," "avg confidence," not Overview's account-wide spend number restated.

**B. Keep and extend the popup/modal drill-down pattern.**
The existing `openM('m-xxx')` modal pattern (click a row/card → modal opens with the full evidence: performance numbers, psychographic detail, reasoning, CTA button) is the strongest UX element in the current build. Every new subpage (Signal, Concept Map, Avatars, Hypothesis Queue, Budget) should use this same modal-drill-down pattern for any list/table row — don't introduce a different interaction model for the new pages.

**C. Variable descriptors must carry their performance data inline, always.**
Anywhere a variable code (CN_, FW_, TN_, ST_, AW_, HP_, PR_, HK_, CTA_) or its descriptor is displayed, its live performance data (CPA/CVR, lift vs. baseline, confidence, sample size) must render directly next to it — not as a separate lookup. This already happens well in a few places (audience intel signal rows); it needs to be the default treatment everywhere a variable is shown, especially in Concept Map and the new Variable Stack views. Also flag: **ST_, AW_, and CTA_ variable families never appear anywhere in the current build** (only CN_, FW_, TN_, HP_, PR_, HK_ are used) — confirm whether that's expected for this account's data or a rendering gap.

**D. Navigable end-to-end flow: Analysis → Strategy → Briefs.**
A user should be able to go from a specific analysis finding (e.g., a Concept Map entry) straight into the Strategy layer that consumed it (Hypothesis Queue or Avatar it informed) and straight into any Brief that was generated from it — via direct links/buttons, not just shared sidebar presence. Right now these three layers are visually separate silos.

## 4. Data-wiring flags (separate from nav, but the nav rebuild will surface these fast — don't paper over them)
- Current build has **zero live backend connection** — no Supabase calls, no API layer, fully static hardcoded numbers for one account (King of Violence). Confirm with Alex whether Replit's actual deployed code differs from this mockup before assuming the nav rebuild is the only work needed.
- **Bookster — the actual pilot account — does not appear anywhere** in the current build. If the nav rebuild ships still hardcoded to KOV only, it's not usable for the pilot.
- The word **"cohort" is currently used only to mean demographic segment** (e.g., "Male 35–44 cohort"). In the architecture, "cohort" is the reserved term for business-model type (ecommerce/lead_gen/service/app). These need distinct UI labels so they don't collide once multi-cohort accounts (like Bookster) are wired in.
- Labels/copy are currently hardcoded to ecommerce funnel language ("purchase," "checkout," "add to cart," "CPA"). A lead-gen/booking account will need these to resolve to `service_18`-block metrics instead. Don't hardcode the new subpages the same way.
- The `metamktg/metrix-iap` GitHub repo is currently **empty** (no commits). If Replit is being treated as source of truth, get this nav rebuild committed there once done — otherwise there's no version history on this change either.
